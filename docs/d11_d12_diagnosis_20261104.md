## D11 (P1): Run Status reports the previous run's operator state as current

### Code path (verified)

There are exactly **two** callers of `generate_run_status.py` (grep over every `*.py`, excluding worktrees):

| Caller | When it runs |
|---|---|
| `run_daily.py:416-418` | At the very END of the daily run, after the run's log (`:378`) and `Last_Operator_Summary.json` (`:395-411`) are written. |
| `run_bk_edge_engine_pipeline.py:101-103` | At the end of the **Edge Engine pipeline**. That pipeline is itself a step *inside* `run_daily` (`run_daily.py:279`, "Edge Engine pipeline"), so this call runs **in the middle of** the daily run. |

What `generate_run_status.py` reads:

1. **"Daily Operator" row.** `CHECKS[0]` (`generate_run_status.py:30-38`) uses the glob patterns `daily_operator_*.log` and `daily_refresh_*.log`. `_latest_file` (`:151-158`) picks the file with the **max `st_mtime`**. The date in the filename, the run identity and the timezone play no part. The age is computed against `fresh_hours=30` (`:174-181`), so a 23.8h-old log is classified as **FRESH**.
2. **DEGRADED reasons.** `_operator_signals()` (`:260-282`) reads `data/tracking/Last_Operator_Summary.json` without checking its `finished_at` or `log` against anything. It turns `blocking_failure`/`failed_steps`, `provider_exhausted_steps` and `degraded_child_outcomes` into DEGRADED reasons (`:276-281`), and `build_run_status` folds them in (`:310-321`).

What `run_daily.py` writes, and when:

- The log name stamp is taken at start (`run_daily.py:289-290`: `datetime.now().strftime(...)`, which is UTC on prod, so `daily_operator_20261103_130000.log`). The file itself is only written once, at the END: `log_path.write_text(...)` at `:378`. **No file exists for the current run until the run finishes.**
- `Last_Operator_Summary.json` is also written only at the END (`:395-411`). It carries `finished_at` and `log`, but no run id and no `started_at`.
- The child outcomes are `data/tracking/_child_outcomes_<parent>.json`. Each parent writes its own as it runs (`refresh_football_props.py:96` → `services/run_outcomes.py:109-125`). They are merged into the summary only at the end (`run_daily.py:387-394` → `run_outcomes.load_all_child_outcomes`, `services/run_outcomes.py:128-143`).

### Why 11-02's log and reasons were chosen during the 11-03 run

At about 13:07Z on 11-03 the operator was running its "Edge Engine pipeline" step. That step finished and called `generate_run_status.py` (`run_bk_edge_engine_pipeline.py:102`). At that moment:

- `daily_operator_20261103_130000.log` **did not exist yet**, because it is only written at `run_daily.py:378`. The newest `daily_operator_*.log` by mtime was therefore `daily_operator_20261102_130000.log`, about 23.8h old, which the 30h window classifies as FRESH. This is a silent substitution.
- `Last_Operator_Summary.json` was still **11-02's file**, because 11-03's is only written at `:406-411`. Its `degraded_child_outcomes` held 11-02's `football_props:...=VALIDATION_FAILED`, which became a current DEGRADED reason.
- 11-03's own `_child_outcomes_football_props.json` had already been rewritten with `UPDATED` by the "Football player props" step (`run_daily.py:52`), which runs before the Edge step. Run Status never reads the sidecars directly, though. It only reads them through the summary, and the summary was the previous run's.

The cause is not a buffering/flush issue, a glob sort-order bug, or a filename/timezone parse. The current run simply has **no persisted identity and no artifact at all** until it ends, and a mid-run caller reads "the latest finished run" as if it were "the current run". The age figure is consistent with this: 23.8h before 13:07Z puts the 11-02 log's mtime at about 13:19Z on 11-02, which is that run's end-of-run write. That figure comes from the ledger and was not verified against prod.

Edge rows from the same mid-run call: "Edge Engine" is current (its log is written at `run_bk_edge_engine_pipeline.py:98` just before the call). "Scorecards" (`all_scorecards_*.log`) is also **yesterday's**, because scorecards run after Edge (`run_daily.py:281`), and it also reads FRESH.

Exposure: `app.load_run_status_context` (`app.py:29934`) serves whatever `Run_Status.json` holds. From the mid-run write until `run_daily.py:417` overwrites it, the site shows the 11-02 reasons as current. If the run is killed before `:417` (earlyoom, unit timeout), the stale file persists.

### A second path to the same symptom (verified in code; impact on prod unverified)

`load_all_child_outcomes` merges **every** `_child_outcomes_*.json` regardless of age or run (`services/run_outcomes.py:128-143`). If a parent step does not run in a given run, that stale sidecar enters the end-of-run summary as current. Two ways this happens:

- the default (no `--continue-on-error`) `break` at `run_daily.py:356-359`;
- a parent whose sport is out of the sport set (`nba_daily`/`mlb_daily` are only added for sports in `--sports`, `:190-197`).

Whether prod runs with `--continue-on-error` is not in the repo, because the bk-daily unit is not tracked.

### Places where "current run" identity could be established

- `run_daily.py:289` `stamp`. This is the only run id that exists today, it is in-memory only, and its format is `YYYYmmdd_HHMMSS` in ambient local time (UTC on prod).
- `run_daily.py:294` "Started:" line. This exists only in the end-of-run log text.
- `Last_Operator_Summary.json` `finished_at` and `log` (`:396-397`). These are written at the end only. There is no `run_id`/`started_at`.
- Sidecar `at` timestamps (`services/run_outcomes.py:119`, UTC). These are per-parent, with no run id.
- Subprocess environment. `_run_step` passes no `env=`, so children inherit `os.environ` (`run_daily.py:223-229`). An exported `BK_OPERATOR_RUN_ID` would therefore reach Edge, generate_run_status and every refresh child without any signature changes.
- There is no lock file or in-progress marker. Systemd's unit start time is outside the repo.

### Proposed minimal fix (not implemented)

1. **Give the run an identity at start.** In `run_daily.main()`, before the step loop, generate `run_id` (the UTC stamp plus pid), `started_at` (UTC ISO) and `log`. Then:
   - atomically write `data/tracking/Current_Operator_Run.json` containing `{run_id, started_at, pid, log, state:"RUNNING"}`;
   - set `os.environ["BK_OPERATOR_RUN_ID"]=run_id`;
   - write `run_id`/`started_at` into `Last_Operator_Summary.json` at the end, and flip the marker to `state:"FINISHED"`.
2. **Make Run Status run-aware** in `generate_run_status.build_run_status` / `_operator_signals`:
   - If a RUNNING marker exists (or `BK_OPERATOR_RUN_ID` is set) and the summary's `run_id` ≠ the marker's: report `operator.state="PENDING"` with `current_run_id`/`started_at`. **Do not fold** the previous summary's reasons into `degraded_reasons`. They may be exposed only as `previous_run: {run_id, finished_at, reasons}`, clearly labelled. The "Daily Operator" row becomes `IN_PROGRESS` for that run instead of picking yesterday's log by mtime.
   - Same rule for the Scorecards row while the current run has not reached scorecards.
   - If the marker is RUNNING but older than a cap (e.g. the sum of step timeouts) and has no matching summary: report `INCOMPLETE (run <id> did not finish)`, never the previous run.
   - Summary with no `run_id` (legacy) and no marker: unchanged behaviour, but show `finished_at` explicitly.
3. **Smallest possible variant**, if (1)–(2) is too much for one change: skip the nested call in `run_bk_edge_engine_pipeline.py:101-107` when `BK_OPERATOR_RUN_ID` is set, because run_daily calls Run Status itself at the end. This removes the observed mid-run write. It does **not** satisfy the acceptance criterion on its own, because a killed run still leaves yesterday's state unlabelled as such. Pair it with at least the `run_id`/`started_at` fields and the "previous run" labelling.
4. **Close the second path.** Have `record_child_outcomes` stamp `run_id` from the environment, and have `load_all_child_outcomes` (or the run_daily merge) include only sidecars whose `run_id` matches the current run. Others are listed as `not_run_this_run`, never as current outcomes.

## D12 (P1): milestone warm-cache guard fails

### Reproduction (this worktree)

`py -3 qc_offline.py qc_perf_guards.py` first failed to import `app` with `ValueError('SECRET_KEY environment variable not set')` (`app.py:99-100`). Re-run with a dummy `SECRET_KEY=qc-local-dummy`, exit 1:

```
[NOTE] keyset cache stable across calls for nfl/mlb/nba/wnba (built once per source version)
[NOTE] _entity_player_known ~0.112ms/call (cheap; no per-row rebuild)
[NOTE] wave participation index built once, reused across 500 lookups (0 extra reads), shared==own-built parity
[NOTE] de-arrow parity: string->object preserves values; build_player_hit_profiles identical arrow vs object (3 profiles)
[NOTE] dashboard vectorizations == original per-row functions (keys, grade, failure signals) on NaN/edge frame
[NOTE] NFL disk materialization: 1 board(s) write a stable-keyed artifact and read back byte-identical (prewarm reaches fresh workers)

[FAIL] build_nfl_milestone_streaks not returning its cached object on a warm call
```

Side effect, inherent to the QC: Guard 7 (`qc_perf_guards.py:249-256`, `:265-276`) deletes and rewrites NFL disk caches under the repo's `data/cache/`. Here it rewrote the gitignored `data/cache/nfl_wave_context.pkl`. `git status` stayed clean. **Do not run this QC on prod as a "read-only" check; it mutates prod `data/cache`.**

### Root cause: a cache MISS on an uncached fail-closed path (not a copy)

`build_nfl_milestone_streaks` (`app.py:50010-50151`):

- **Key.** `_sig = (_nfl_player_log_signature(), _nfl_injury_source_state()['mtime'], _nfl_expected_completed_week(), min_run, limit)` (`:50023-50024`). The log signature is `(relpath, size, mtime_ns)` per source file (`app.py:31240-31257`). It is process-stable and contains nothing per-request or time-of-call.
- **Memory hit.** `return _NFL_MILESTONE_CACHE['data']` (`:50027-50028`) returns the same object, with no copy and no deepcopy.
- **Disk hit.** `_nfl_disk_cache_load` (`:50031-50035`) unpickles a **new** object, but stores it in `_NFL_MILESTONE_CACHE` first, so the *next* call returns that same object. A disk hit on call 1 does not break `m1 is m2`.
- **Store.** This happens **only** at the end of a successful build (`:50147-50150`).
- **The defect path.** `:50040-50041`: `if df is None or df.empty or '_key' not in df.columns or 'week' not in df.columns: return {**base, 'unavailable_reason': 'no_game_stat_logs'}`. The same applies to `:50043-50044` (`no_season_column`). These return a **freshly constructed dict and never populate the cache**, so every call is a miss and a new object.

In this worktree the gitignored NFL player logs are absent. `data/historical/` has no `NFL_PlayerStats_202*.csv`, there is no `data/tracking/_nflverse_stats_20*.parquet`, and there is no `jw26.parquet`. So `_nfl_player_log_sources()` returns `[]` and the builder takes the uncached path every time. The probe (`scratchpad/d12_probe.py`, with the disk cache redirected to a temp dir) printed:

```
player-log sources: []
sig#0 ok; len(logsig)=0 inj_mtime=0 week=(8, 2026)      (sig identical on both evaluations)
cache after call1 keys: []
call1 2.7ms call2 1.9ms  m1 is m2: False  m1 == m2: True
available: False unavailable_reason: 'no_game_stat_logs'
```

Control run: same code, same probe, with `DATA_DIR` pointed **read-only** at the main checkout's `data/` (7 sources: 2020–2025 CSVs plus the 2026 parquet) and the disk cache redirected to temp:

```
cache after call1 keys: ['sig', 'data']
call1 8231.2ms call2 33.5ms  m1 is m2: True
available: True season: 2026 through: 4 totals: 45 25
```

So the cache is correct whenever the data exists: a stable key, a hit on the warm call, and the identical object at 33.5 ms, under the 200 ms ceiling. The guard failure is a **local-data artifact**: a cache miss caused by the fail-closed early return, which is not cached. It is not a key instability and not a copy-returning cache. The 11-03 observation was most likely made in a tree without the gitignored NFL logs, such as a worktree. Which tree was used is not recorded, so that part is unproven. Prod has these files per CLAUDE.md §13 (2023–25 copied, parquet fetched in run_daily), so Guard 3 should pass there. That was not verified; see the check below.

### Is the guard's expectation right?

**Yes, for the available path.** Returning the shared cached object is the design: the in-memory dict hands back the same object, and the three app callers only read it (`app.py:46345` `_gl_adapt_milestone_streaks`, `:50619` template render, `:51422` matchup center). No caller mutates the result, so no copy-for-mutation-safety is intended. A copy-returning cache would also break the guard by design, which is fine because that is not this code. Where the guard is wrong:

1. It is **data-dependent**. With no local logs it reports a perf regression that does not exist. It should distinguish "unavailable" from "uncached".
2. Its `except Exception → note "skipped"` hides real errors as passes, while the no-data case is reported as a FAIL. That is backwards.

### Proposed minimal fix (not implemented)

**Preferred: fix the guard, not app.py.** Make Guard 3 fixture-driven and data-independent, mirroring `qc_nfl_milestone_streaks.py:60-67`:
- Monkeypatch `_nfl_player_week_data` with a small fixture and a counter, `_nfl_player_log_signature` with a constant, `_nfl_injury_source_state` with a constant `mtime`, `_nfl_expected_completed_week` with a constant, and `_nfl_disk_cache_load`/`_nfl_disk_cache_store` with no-ops (this also stops it writing `data/cache`).
- Assert: (a) `m1 is m2`; (b) `_nfl_player_week_data` was called exactly once across both calls (rebuild count, the real invariant); (c) changing the patched signature forces a rebuild (count 2, new object); (d) warm ≤200 ms as a secondary ceiling only.
- Optionally keep a real-data variant that reports `SKIP (no local NFL player logs: unavailable_reason=...)` when `m1['available']` is False, instead of FAIL.

**Optional app.py change**, only if repeated calls on unavailable data are considered a cost: also memoise the `no_game_stat_logs`/`no_season_column` results under the same `_sig`, in memory only and never on disk. The signature covers the file manifest, so newly arriving files invalidate it. Caveat: `_nfl_player_week_data` swallows per-file read errors (`app.py:31271-31279`), so a transient read failure with an unchanged signature would stay pinned until a file changes. That is why this is not the recommended minimal fix. Existing QCs that swap fixtures already `.clear()` the cache before rebuilding (`qc_streak_integrity_milestone.py:96, 101`; `qc_nfl_milestone_streaks.py:117`), so they would be unaffected.
